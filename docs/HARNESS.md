# Harness

Harness replaces the visible Knowledge destination in the shared desktop/web frontend. Memory remains the default section with its existing reviewed observations, source filters, permissions and revocation behavior. Old `?view=knowledge` links resolve to Harness; `?view=harness&harness-section=repository` opens repository context directly. The internal route identifier remains `knowledge` for compatibility with existing setup callbacks.

Repository context reads the existing local-only autonomy API. It displays monitor freshness, the exact Git revision, tracked instruction paths/hashes and lossless storage evaluation results. Version-bound approve/decline and pause/resume actions reuse the backend's fencing. Offline, paused and historical snapshots cannot be approved or previewed as current. Failed reads disable decisions. Approved contents are fetched only when requested and rendered as text, never HTML.

Skills & tools links to actual supported configuration flows. It does not claim to detect installed packages or runtime readiness. Activity exposes the bounded storage-evaluation history, not invented agent runs. Every non-empty valid instruction snapshot is evaluated for approval, whether or not it contains duplicates. The next monitor cycle backfills old snapshots without reopening existing decisions. Empty instruction inventories stay audit-only.

The Pi-only approved-context reader verifies source hashes, paths, schema and byte limits. `/relay-context` records the exact snapshot and a digest in Pi without starting a model. `/relay-context-review` explicitly requests review by the user's configured provider. No builtin shell or filesystem tools are enabled. Provider usage and responses stay in Pi session history. Old snapshots already read into a session cannot be retroactively removed by pausing retrieval.

Run a trial offers one `bug_investigation_v1` attempt on selected saved work. The server assembles current case evidence, applicable reviewed memory and an approved instruction snapshot. The user previews the exact context and SHA-256 digest, selects 30–120 seconds and explicitly authorizes provider usage. Admission requires the same digest, case revision and current approved snapshot. Combined context is capped at 96 KiB without silent truncation. It reuses the durable Hermes queue and idempotency, not a second executor. Changed or paused instruction context invalidates queued dispatch and requests a cooperative stop for running work. Existing source and memory freshness checks remain active.

The trial uses the configured runtime's existing tools and requests no source edits, external messages or memory publication. It is not a sandbox or a hard spending cap. Results, actual evidence, reported usage and stop controls remain in Work. A model response marked completed does not establish reproduction or verification. An uncertain start retains the same request identity for retry; a stale preview requires inspecting Work before preparing another attempt. No automatic model call happens while opening or previewing a trial.

For an already-running development installation, restart the API with its existing Hermes configuration and reopen the rebuilt desktop app to activate this change. The next repository-monitor heartbeat can then evaluate an existing unique snapshot. Review that snapshot before opening Run a trial; approval alone does not start an attempt.

This release does not import arbitrary skills, install MCP servers, infer safe test commands, write repository instructions or run before/after quality comparisons. It does not add a new Tokio runtime; Relay already uses Tokio. Isolated patch verification and comparable baselines remain separate milestones before reporting an improvement.

They cover exact content receipts, invalid paths, tampered/oversized bodies, unavailable approval, navigation compatibility, displayed-version decisions, preview invalidation, failed services and narrow layouts. This is separate from a live provider review or measured optimization.
